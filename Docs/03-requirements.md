# المتطلبات وقصص الاستخدام

معرفات ثابتة. «الأول» يعني مطلوب في إصدار usable لكلا المسارين. يمكن بناء الأعمال على مراحل حسب [الخريطة](11-roadmap.md). المتطلبات هنا تصف المخرجات؛ مخطط البيانات والعقود موضّحان بشكل منفصل.

| ID | المتطلب | معيار القبول |
| --- | --- | --- |
| R01 | أنشئ مشروعًا داخل Workspace، بنوع تصميم جديد أو تغيير قائم | لا يمكن رؤية مشروع خارج Workspace المصرح؛ لكل mode نقطة بدء واضحة |
| R02 | حوّل وصف AR/EN أو نموذج يدوي إلى متطلبات قابلة للتعديل | عند غياب parent CIDR أو عدد hosts أو سياسة مؤثرة، يُطرح سؤال أو يُعرض اقتراح صريح؛ لا يولَّد تصميم قابل للمراجعة حتى تُحسم الحقول المانعة |
| R03 | استورد لقطة منسقة، وملفات Cisco ذات نطاق دعم محدد | تظهر تغطية الاستيراد والأجزاء غير المفهومة والمصدر لكل حقيقة. تأكيد اللقطة يثبّتها؛ استيراد جديد ينشئ لقطة جديدة |
| R04 | أنشئ وعَدّل تصميمًا منطقيًا وفيزيائيًا | أي وصلة لها واجهتان صالحـتان ضمن profile؛ يستطيع المستخدم تغيير التوصيل بشكل صريح؛ تعديل موضع الرسم لا يغيّر تحقق الشبكة |
| R05 | ابْنِ خطة IPv4/VLAN وربط gateway والمنافذ | يطابق كل قسم السعة المعلنة والحجوزات؛ أي overlap أو خروج عن parent أو port exhaustion يمنع اعتماد التصميم |
| R06 | قارن بديلين و/أو baseline وcandidate | الفرق يميّز الإضافة والإزالة والتعديل مع أثر السعة والسياسات وما تعذر تحديده. مقارنة بديلين من نفس intent؛ مقارنة تغيير من baseline ثابت |
| R07 | افحص النموذج وأعد الفحص بعد التعديل | لكل finding قاعدة ونطاق وأثر؛ لا يختفي الخطأ من نتيجة النسخة بمجرد تجاهله؛ نتيجة قديمة تصبح stale عند تغيير المدخلات |
| R08 | كوّن مراجعة من مهندس ومراجع مع أثر تدقيقي | رافض/موافق يحدد revision وبصمة الأدلة. تغيير المراجعة أو التصميم يقتضي إعادة التقييم؛ استثناء بمالك وسبب وانتهاء لكل سياسة تسمح به |
| R09 | صدّر حزمة تصميم/تغيير وتراجع | تتضمن التنفيذ اليدوي، المغيَّر، القيود، الفحوص ونسخ الأدوات. عند unknown مانع أو عدم دعم CLI يمكن تصدير نسخة review فقط، بدون ادعاء جاهزية التنفيذ |
| R10 | اعرض دليل اختبار Cisco من معمل خارجي | fixture معلوم ومنصة ونسخة وخطوات تحقق ونتائج متوقعة/فعلية؛ أي حالة غير مجرّبة تظل untested |
| R11 | شغّل Self-hosted بدون إرسال ملفات الشبكة خارجيًا | يُنفّذ المساران دون مزود خارجي؛ يمكن للإداري تمكين مزود معتمد وإظهار ما يُرسل قبل الاستخدام |
| R12 | احفظ العمل وافتحه وقارن النسخ لاحقًا | round trip يحفظ IDs والوصلات وتخطيط المستخدم والـrevision، ويتم استئناف المهمة بعد تحديث الصفحة |

## مساران رئيسيان

**تصميم جديد:** مشروع → وصف عربي أو إدخال يدوي → متطلبات وسياسات صريحة → بديلان مثل راوتر بسويتش واحد أو توزيع endpoints على سويتشين مدعومين → مقارنة حسب التكلفة التقريبية وعدد المنافذ والسعة ونقاط الفشل، مع إظهار مصدر تقدير التكلفة → حفظ بديل → تحقق → مراجعة → تقرير وحزمة مختبر.

**تغيير قائم:** مشروع → استيراد baseline وتأكيد التغطية → طلب إضافة Guest VLAN → تحويل الطلب لمتطلبات وسياسات → مرشح يحتفظ بالأجهزة والمنافذ التي لا يلزم تعديلها → عرض الفرق وعلى الأقل بديل ثان عند وجود خيار حقيقي (مثلاً مصدر سعة منافذ مختلف) → التحقق من أن الخدمات الحالية بقيت وفق نطاق الأدلة → مراجعة وتصدير تغيير وتراجع يطبقهما المهندس.

الحالات السلبية المطلوبة: ملف جزئي، قسم أكبر من المجال، link بلا منفذ، خياران غير ممكنين، provider غائب، دليل قديم، موافقة على revision أقدم، تعذر التحميل، وتعذر التصدير. إذا كان البديل الثاني مخالفًا للقيود، يُعرض كغير قابل للتنفيذ مع السبب أو تعرض عدم إمكانية توليده؛ لا تُخترع نتيجة.
